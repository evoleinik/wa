# Sending a WhatsApp message from box through WhatsApp for Mac

**Type:** Decision doc
**Date:** 2026-11-24
**Status:** decided, A with Return first

## Problem

Eugene wants to send one WhatsApp message from box, as himself, through WhatsApp for Mac
on air. The first use is a cold business contact in Indonesia, so a number that is in no
chat must work. Every send needs his explicit OK. A ban on his main number would be
costly. Meta flagged a scripted run on another Meta product on 2026-11-09.

## What air has today (checked 2026-11-24)

- WhatsApp for Mac 26.47.12 on macOS 15.8.1. It has no AppleScript dictionary.
- It registers the `whatsapp://` URL scheme. `whatsapp://send?phone=<digits>&text=<text>`
  opens the chat with the text in the composer. It does not press Send.
- Over SSH, `osascript` can ask System Events which app is in front. Pressing a key or
  reading another app's window fails with "osascript is not allowed assistive access".
  SSH logins answer to sshd for Accessibility, as they do for Full Disk Access.
- sudo on air needs Eugene's password, so only he can install a new launcher.

## Criteria (fixed before ranking)

1. Account risk. Does WhatsApp's server see anything other than its own app sending?
2. New numbers. Does it reach a number that is in no chat?
3. Exposure. What new grant does air give, and to what code?
4. Wrong-target risk. Could the text land in another chat or another app?
5. Proof. Can wa show the message really left?
6. Upkeep. How often does a WhatsApp update break it?

## Options

A. **URL scheme, then press the Send button through Accessibility, from wa-launch.**
   wa-launch gets the Accessibility grant next to Full Disk Access. wa opens the URL,
   finds the composer by its exact text, presses the button next to it, and reads the
   message back from the database.
   - Strongest counterargument: wa-launch then holds two grants. Anything that can run it
     as Eugene can send messages, not only read them.
   - Failure mode: a WhatsApp update renames the button. wa then exits without sending
     and leaves the text in the composer.
B. **URL scheme, then a Return key press through System Events.**
   - Strongest counterargument: the key goes to whatever app is in front. If Eugene is
     typing on air at that moment, his keys or the Return can land in the wrong place.
     It also needs an extra Automation grant for System Events.
   - Failure mode: focus moves between open and key press, and the Return goes elsewhere.
C. **A Shortcuts shortcut that uses WhatsApp's own "Send Message" intent.**
   - Strongest counterargument: the intent takes a contact, so a cold number fails.
     Eugene must build the shortcut by hand in the Shortcuts app.
   - Failure mode: the intent asks for confirmation on screen and the run hangs.
D. **An unofficial WhatsApp Web library (Baileys, whatsapp-web.js).** Ruled out by the
   brief. It logs in as a second, unofficial device. That is the ban risk this doc exists
   to avoid.

| | Account risk | New numbers | Exposure | Wrong target | Proof | Upkeep |
|---|---|---|---|---|---|---|
| A | none, the real app sends | yes | Accessibility on wa-launch | low, checks the composer text first | DB read-back | button lookup |
| B | none | yes | Accessibility + Automation | high, frontmost app | DB read-back | low |
| C | none | no | none new | low | DB read-back | shortcut by hand |
| D | high | yes | none on air | low | yes | high |

Facts that would change the ranking: WhatsApp adding AppleScript or a CLI (then use it).
The Accessibility tree hiding the Send button (then B, guarded by a frontmost check).
WhatsApp's intent accepting a bare phone number (then C needs no new grant).

## Recommendation

A. It is the only option that reaches new numbers, needs no second device, and cannot
type into the wrong app. The extra grant goes on a binary that already runs only one
root-owned copy of wa, and wa only sends after `--yes`.

## Questions for Eugene

1. (Exposure) Is it fine that wa-launch holds Accessibility as well as Full Disk Access?
   The default is yes. The other way is a second launcher holding only Accessibility.
   Answer, 2026-11-24: yes. He ran install.sh and granted wa-launch Accessibility.
2. (Proof) Which number should the test send go to? Your own number opens the
   "Message yourself" chat.
   Answer, 2026-11-24: his own number.

## Decision — 2026-11-24

A, with one change found in the live test. wa-launch holds Accessibility. wa opens the
URL in the background, checks the composer holds the exact text, and presses Return in
WhatsApp only. The Send button and a frontmost Return are fallbacks.

## Outcome

- First live send: AXPress on the button that matched "send" returned ok and sent
  nothing. wa exited 5 as designed, and nothing reached the chat.
- wa then learned to check the composer after each try. Second live send: the Return key,
  posted to WhatsApp's process with the composer focused, sent it. Read-back found it,
  message #161580 in the "You" chat at 21:04. Return is now tried first.
- The self chat and new chats can be filed under an `@lid` id with no phone number.
  `whatsapp://send?phone=` still reaches them, and read-back accepts an `@lid` chat.
- Still open: which button the "send" label matched. `wa send ... --check` names it and
  sends nothing.
